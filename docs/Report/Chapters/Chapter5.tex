Chapter~\ref{ch:concepts} describes the concept of the VR museum. This chapter explains its implementation, including the choice of technology, the modular structure, the input methods, and the process from a search query to a new exhibition.

\section{Technology Decisions}
\label{sec:implementation-technology}

\paragraph{Godot and OpenXR} The application uses Godot 4.6.2 with .NET and its built-in OpenXR interface \citep{godotOpenXR,godot462}. OpenXR allows the same application to communicate with different XR runtimes \citep{khronosOpenXR}. Godot XR Tools complements this interface with reusable scenes and scripts for building XR applications \citep{godotXRTools}. The OpenXR Vendors Plugin adds the loaders and extensions required by individual headset platforms \citep{godotOpenXRVendors}. Separate export profiles build Android applications for Meta Quest and VIVE Focus. The Windows profile uses the active OpenXR runtime for PC streaming. The museum room and core workflow remain the same. Input and rendering, however, depend on the platform.

\paragraph{Application Layers} The C\# code is divided into separate .NET projects so that search logic and media access do not depend on Godot scenes. Godot handles input and presentation, while libraries contain the application logic and adapters for external services. A factory connects these parts. It uses the current server address and the media paths for the selected platform.

\paragraph{Vitrivr and Media Delivery} Developing a new search engine was outside the scope of this thesis. The museum sends text and vector queries to the vitrivr-engine through its HTTP interface. Separate ingestion pipelines store the descriptors of images, videos, and 3D models in the shared \texttt{clip} field. The vitrivr Python Descriptor Server calculates these vectors \citep{vitrivrPythonDescriptorServer2026}. PostgreSQL stores them with pgvector \citep{pgvector2026}. Nginx serves the corresponding media files separately \citep{nginxStaticContent2026}.

The health service checks the backend before entry. The descriptor server and PostgreSQL database are also omitted. They create and store the searchable data before visitors use the application.


\section{Key Implementation Components}
\label{sec:implementation-components}

\paragraph{Godot Integration} \texttt{ServerValidationController} checks the backend before entry. Once this check succeeds, \texttt{SearchController} submits the configured initial query. Later searches start from entered text or from the CLIP vector stored in a selected exhibit. The controller rejects a new query while another search is running. It gets the available placement areas from \texttt{MediaPlacementController} before calling the application. \texttt{PlayerHandInput} handles hand-tracked input, while \texttt{Original\allowbreak Size\allowbreak Controller} manages the separate viewing rooms for 3D exhibits.

\pagebreak
\paragraph{Application Layer} The \texttt{IMuseum\allowbreak Application} interface gives Godot access to the application logic. \texttt{Museum\allowbreak Application} forwards searches to \texttt{Search\allowbreak Media} and reachability checks to \texttt{Validate\allowbreak Server}. For each search, \texttt{SearchMedia} creates the query and sends it to the configured search engine. It then selects results that match the chosen media types and the available 2D and 3D capacity. The selected files are loaded concurrently. A file that cannot be loaded is left out of the final result.

\paragraph{Infrastructure and Server Integration} \texttt{Vitrivr\allowbreak Search\allowbreak Service} translates queries and responses for the vitrivr-engine. Its response parser keeps the ranking order and removes duplicate file paths. It also keeps the start time of video segments and maps 3D source paths to their runtime PCK packages\footnote{A PCK file is a Godot resource package that can be loaded at runtime.}. \texttt{MediaLoader} first looks for a local file and uses Nginx only when it needs to download the media. Server validation is handled separately from the search. The interfaces also separate the application logic from Godot and from the specific server implementations.

\section{Interaction Input Implementation}
\label{sec:implementation-interaction-input}

Controller input uses the OpenXR action map and Godot XR Tools. The right trigger controls the pointer used for selection. Holding the left grip shows the text-search interface, while the right grip manipulates grabbable objects. The right joystick controls movement, the left joystick controls turning, and pressing the left joystick switches between the menu and the museum.

For hand tracking, \texttt{PlayerHandInput} first determines whether the application is using controllers or hand tracking. \texttt{HandGestureInput} maps a right-hand pinch to the same pointer action as the controller trigger, while grab values handle the pickup actions. This keeps selection and manipulation consistent across the two input modes.

A short left-hand pinch switches between the menu and the museum. If the pinch is held beyond the configured delay, \texttt{HandJoystickMovement} shows a virtual joystick and derives movement and turning from the direction of the tracked hand. Pickup is disabled during a pinch. This prevents the system from treating the same hand movement as two different actions.

The placement controller separates the results by media type. For each wall area, the 2D strategy chooses a random number of places up to its configured maximum. The wall is then divided into equal sections. It creates one image or video exhibit in each section and adapts the frame and collision shape to the content, conceptually shown in Figure~\ref{fig:concept-presentation-templates}. Videos initially show a preview and start at the retrieved time when a visitor approaches.

The 3D strategy assigns one result to each floor area. It loads the model from its PCK package and scales the base of the pillar-and-sphere display to the size of the area before fitting the model inside the glass sphere. The same strategy can therefore handle placement areas of different sizes. The stored model bounds are also used when the \emph{Original Size} action moves a model into a separate viewing room.

The previous exhibition stays visible while the search is running and files are loading. A query or response error leaves it unchanged. After a successful search, the controller replaces the 2D exhibits and then the 3D exhibits one after the other. A valid result without displayable media clears the exhibition. Files from the previous search are released from storage after placement has completed.

\section{Data Preparation and Deployment}
\label{sec:implementation-deployment}

Standalone headsets have less processing power and memory than the backend server. The media pipeline therefore standardizes files before indexing and records its steps and errors in a report. It first creates a timestamped backup. Images become JPG files with a maximum size of 2048 pixels in either dimension. Videos become OGV files. Their longest dimension is limited to 2048 pixels and their frame rate to 30 frames per second. The 3D pipeline converts supported assets to binary glTF (GLB) and validates the result. The museum supports static, surface-based models, so the pipeline rejects animations and point clouds. It also rejects models with more than 1.5 million rendered triangles. Embedded textures are limited to 2048 by 2048 pixels. The application does not load GLB files directly. Instead, the pipeline starts Godot without a graphical interface and imports each GLB file and creates a PCK package for it. Vitrivr searches the GLB representation, while the museum loads the imported scene from the PCK package.

The Quest, Focus, and Windows builds use separate rendering profiles for resolution scale and refresh rate. An external \texttt{config.json} provides the server address, tutorial setting, and initial query, allowing the server to be changed without rebuilding the application.
